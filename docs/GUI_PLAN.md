# План: графический интерфейс для BrowserOxide (headless и headed сборки)

Статус на 2026-09-30: этап 0, веха M1, основная часть этапа 1 и этап 2 в согласованном объёме (модуль `text`, фолбэк по шрифтам) и начало этапа 3 (режим `Full`: `calc()`, сетка, строчная раскладка) выполнены (см. раздел «Выполнено»; что отложено и почему — там же), остальное не начато.

## Выполнено

**Этап 0 (каркас).**
- Крейт `browser_oxide_shell` (`publish = false`, `rust-version = "1.95"`, eframe 0.36 / glow). Член воркспейса, но не в `default-members`: голый `cargo build` остаётся headless.
- Фича `paint` в `browser_oxide` (пустая по зависимостям). Весь код отрисовки и запись стилей в раскладке — за ней.
- `host::EngineHandle::load_html` и `::screenshot` (под `paint`).
- CI: MSRV-задача собирает воркспейс без оболочки; шаг «в дереве `browser_oxide` нет оконных зависимостей»; шаг `cargo check -p browser_oxide --all-targets` без `paint`.
- Не сделано из этапа 0: расширение `host` до интерактивных каналов команд/событий (нужно с этапа 5), проверка лицензий `cargo deny` (утилиты нет на этой машине — сделает CI-задача `deny`).

**M1 (скриншоты-MVP).**
- `layout::paint_tree`: плоский список боксов с абсолютными координатами, унаследованными `color`/`font-size`/`font-weight`/`font-style`/`visibility`, `opacity`, клиппингом `overflow`.
- `paint`: фон (с распространением с `html`/`body` на весь холст), рамки, текст с переносами, простые рамки контролов форм, заглушка для `<img>`.
- `Page::screenshot(&ScreenshotOptions { full_page })`, `examples/screenshot.rs`, окно оболочки с адресной строкой (URL или путь к .html), прокруткой и переключателем «Full page».
- Тесты: `tests/paint_screenshot.rs`, `tests/host_paint.rs`, юнит-тесты `paint` и оболочки.

**Этап 1 (единый движок стилей) — основная часть.**
- Модуль `style`: `Stylist` (все правила документа с origin, `!important`, `@layer`, `@media`, `@supports`, вложенностью `&`, индекс по правому id/class/tag; решает каскад один раз), `StyleTree` (проход сверху вниз с наследованием, `font-size` в px, `em`/`%`/`rem`), `custom` (пользовательские свойства и `var()`), `hints` (презентационные атрибуты), `ua.css` (UA-таблица; таблицы, контролы форм и рамка iframe исключены сознательно — причины в комментарии внутри файла).
- Раскладка берёт стили из `StyleTree` (кеш по `dirty_epoch`); `getComputedStyle` читает тот же `Stylist`. Атрибут `style` — часть каскада (author, выше любого селектора), проигрывает author `!important`, в том числе для предков при наследовании.
- Шорткаты: `gap`, `flex`, `flex-flow`, `background` (только цвет), `border-color/width/style`, `font`, логические `margin-inline` и т. п. (горизонтальный LTR), `place-*`, CSS-wide ключевые слова на шорткатах. В раскладку теперь доходят `gap`, `align-*`, `justify-*`, `flex-basis`.
- `var()`: подстановка как текст на элемент (наследование, ссылки между свойствами, fallback, циклы), в раскладке и в `getComputedStyle`, включая `getPropertyValue('--x')`.
- Тесты: `tests/style_engine.rs`, юнит-тесты `style::*`, `css_values::shorthand`.

Не сделано из этапа 1, с причинами:
- **Псевдоэлементы** `::before`/`::after`/`::marker`/`::placeholder` (S7). `Stylist` отбрасывает такие правила. Нужна генерация боксов в раскладке, то есть дерево боксов этапа 3; до него результат некуда положить.
- **Состояния** `:hover`/`:active`/`:focus`/`:focus-visible`/`:checked` (S8). Их выставляет ввод (этап 6); поля без источника значений были бы заготовкой.
- **Инкрементальная инвалидация** и bloom-фильтр предков (остаток S9). Сейчас `StyleTree` пересчитывается целиком по `dirty_epoch`. Не мерилось на больших страницах; решение по замерам. Правила с `var()`/`--x` (`Rule::dynamic`) разбираются заново на каждом элементе, а не один раз при загрузке листа — потолок производительности на страницах с тысячами элементов и `var()`-тяжёлым CSS.
- **Свойства без реализации** (остаток S6): `border-radius`, `background-image`, `text-decoration`, `text-transform`, `letter-spacing`, `box-shadow`, `outline` и др. Разбор без отрисовки ничего не даёт, их добавит этап 4 вместе с рисованием.
- **Приближения:** вложенные `@layer` регистрируются плоско (правило прямо в `a` ранжируется ниже `a.b`, хотя должно выше); `@supports` считается истинным, кроме `not`; `@container`, `@scope`, `@import` пропускаются; `--x: initial`/`inherit` для пользовательских свойств не особый случай; `calc()` в длинах раскладка не понимает и без `var()` (значение считается `auto`).
- **Критерии выхода этапа из плана:** `BENCHMARK.md` (routed 118/126) не прогонялся — нужна живая сеть и защищённые сайты, прогон остаётся за владельцем.

Проверено (macOS arm64, rustc 1.97.1): `cargo fmt --all -- --check`; `cargo clippy --all-targets --workspace --features browser_oxide/paint -- -D warnings` и `cargo clippy --all-targets -p browser_oxide -- -D warnings` (без `paint`); `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --workspace`; `cargo test --workspace --features browser_oxide/paint --no-fail-fast -- --test-threads=1`; `cargo tree -p browser_oxide -e normal,build` (с `paint` и без) не содержит winit/egui/eframe/glutin/wgpu/softbuffer.

Первая версия этапа давала `reload_html_static` 81 мкс (+198%): каждое создание состояния документа глубоко клонировало UA-таблицу `Stylist`. Исправлено: `Stylist` хранит правила, индексы и слои под `Arc` с копированием при записи, клон происходит только когда страница добавляет свой CSS. Бенч `reload_html_js` падает и на базе (`no reactor running` в `op_timer_sleep`: бенч не входит в рантайм tokio) — в замер не вошёл, это дефект самого бенча.

**Этап 2 (текст и шрифты) — начало.**
- Модуль `text`: база шрифтов, разбор `font`, таблица метрик, шейпер, растеризатор глифов и сами вшитые шрифты (`text/fonts`) вынесены из `canvas/text`. Canvas строит на нём метрики и рисование (`canvas/text.rs`); вывод canvas не менялся (`png_byte_parity`, `font_metrics`, `chrome147_parity`, `canvas_paths` зелёные).
- `text::fallback`: для символа, которого нет в запрошенном шрифте, берётся первое лицо из списка: сначала зарегистрированные приложением (`register_fallback_face`), затем вшитые `Noto Sans`, `DejaVu Sans` (кириллица, греческий, арабский, иврит, армянский, грузинский, символы), `Noto Sans Thai`, `Noto Sans Devanagari` (`text/fonts`, OFL-1.1, происхождение и SHA-256 в `text/fonts/SOURCES.txt`). Используется только отрисовкой (`paint`); `Canvas2D::fill_text_with_face`/`measure_text_with_face` рисуют лицо по байтам, минуя базу шрифтов. Canvas, `document.fonts`, `FontFace.load` и `measureText` не затронуты, фолбэк-лица в базе не числятся (`BUNDLED_FACE_COUNT` прежний).
- CJK и эмодзи движок не вшивает и сам с диска не читает: приложение подаёт шрифты через `register_fallback_face`. Оболочка делает это по флагу `--host-fonts` (выключен по умолчанию; список путей в `browser_oxide_shell`), пример `screenshot` — по `--font <файл>`. Шрифты хоста влияют только на пиксели: ширины для DOM-API от них не зависят (в раскладке 0.6em на символ, для canvas — таблица метрик). Это сознательное отступление от §4 п. 3 («шрифты из профиля, не с хоста»), согласованное для отрисовки окна; инвариант движка «`fontdb` без `fs`, `Source::Binary`» сохранён.
- CSS `font-family` доходит до отрисовки (`PaintStyle::font_family` → `PaintBox`): serif и monospace рисуются Liberation Serif/Mono, а не одним sans. Без заданного семейства берётся начальное значение `serif`, как в браузерах. Ширины заявленных профилем семейств (например Georgia) идут из таблицы метрик, а глифы рисует шрифт-заменитель, поэтому межбуквенные промежутки в таком тексте местами неровные — это следствие выбора «метрики из профиля, а не с хоста».

Не сделано из этапа 2:
- **Монохромный Noto Emoji** (`NotoEmoji[wght].ttf`, 1 982 596 Б) не вшит: в разы больше оценки «сотни КБ». Без него в headless-снимках эмодзи рисуются только теми символами, что есть в DejaVu, остальные — «тофу»; в окне с `--host-fonts` — цветные эмодзи хоста.
- Измерение текста шейпером в раскладке (headless продолжает считать 0.6em на символ — его заменит IFC этапа 3 вместе с переключателем раскладки, иначе меняется геометрия всех страниц без сравнения с Chrome); UAX#14/bidi/графемы; `@font-face` и WOFF/WOFF2; `document.fonts` с реальными состояниями.
- Фолбэк выбирается по первому лицу, покрывающему символ: язык (`lang`) не учитывается, ханьцзы в китайском и японском тексте рисуются одним и тем же лицом.

**Этап 3 (раскладка) — основная часть.** Решения по дизайну (раунд вопросов): свой IFC на `rustybuzz` + `unicode-linebreak`, а не `parley`; раскладка меряет только герметичными лицами (вшитые + таблица метрик профиля), CJK/эмодзи дают фиксированные advance'ы (`unicode-width`), шрифты хоста — только пиксели; переключатель `LayoutMode::{Legacy, Full}`; эталон — локальный Chrome; порядок работ из §3 этапа 3.
- **`LayoutMode`** (`layout/mod.rs`): `Legacy` — прежняя приблизительная раскладка, заморожена (тест `legacy_layout_is_frozen`); `Full` — строящаяся. Режим по умолчанию процесса (`layout::set_default_mode`, его ставят оболочка и пример `screenshot`) и `Page::set_layout_mode` для одной страницы. Headless по умолчанию остаётся `Legacy`. User-agent-лист в `Full` дополняется таблицами (`style/ua_full.css`), в `Legacy` — нет.
- **Корпус против Chrome** (`tests/layout_corpus/`): 44 самописные страницы, 149 элементов; эталоны снимает `snapshot.mjs` локальным Chrome по протоколу DevTools (окно 1512×871 = профиль; шрифты в страницах — `Arial`/`Times New Roman`/`Courier New`, метрически совместимые с вшитыми Liberation). Элемент совпал, если `getBoundingClientRect` и `getClientRects` в пределах 1px. Тест `layout_corpus`: `Legacy` **53/149** (равенство; на исходных 96 элементах — 49, он не сдвигался), `Full` **147/149** (пол). Новые 12 страниц добавлены уже после того, как раскладка была написана, и совпали на 41 из 44 элементов на первом прогоне — по ним видно, что раскладка обобщается, а не подогнана под исходные 30.
- **Реальные страницы** (`tests/layout_corpus/real/`, не в git): `prepare.mjs` делает сохранённую страницу самодостаточной (локальные стили внутрь, без скриптов и картинок) и одинаковой по шрифтам для обоих движков (веб-шрифты убраны, `font-family` сведён к `Arial`/`Times New Roman`/`Courier New`, метрически совместимым с вшитыми); `snapshot.mjs --real` записывает прямоугольники всех элементов в порядке документа; `probe.mjs` выполняет выражение в Chrome на странице (чтобы понять, что именно делает Chrome); тест `layout_corpus_real` сравнивает и печатает расхождения по тегам и первые примеры (`LAYOUT_CORPUS_REPORT=1`), пол хранится локально в `real/floors.json`. Первый набор — шесть страниц `rustdoc` этого репозитория (8373 элемента): `Full` **53.6%** (`Legacy` 7.2%). Второй — пять сохранённых страниц (`fetch.mjs` скачивает страницу и её стили в `real/_src/`; HN, `example.com`, gnu.org, учебник docs.python.org, статья Википедии «Rust»): `Full` HN **97.3%**, `example.com` 100%, gnu.org 46%, Python 7%, Википедия 10.5% (`Legacy` по всем 21048 элементам 9.2%, `Full` 31.9%). Эталоны снимаются настоящим Chrome с `--force-device-scale-factor=2` (окно 1512×958 даёт вьюпорт 1512×871), а не эмуляцией метрик устройства: эмуляция округляет в CSS-пикселях (строка Arial 16px — 18, а не 18.5), настоящий масштаб — в физических; тест сверяет DPR. Работа идёт по принципу «чини первое расхождение»; это нашло: строгий разбор `@media` (в `Full` — отдельный вычислитель; прежний лениво считал `(min-width: …)` истинным и открывал мобильные правила), атрибуты таблиц старой вёрстки (`width`, `cellpadding`, `cellspacing`, `border`, `align`, `valign`, `bgcolor` — только в `Full`, как подсказки между UA-таблицей и авторскими правилами), блоки внутри строчных (строчный контекст разрывается, блок идёт отдельным; Chrome отдаёт `getBoundingClientRect` строчного элемента вместе с анонимным блоком), корень документа как контекст форматирования блоков (поля `body` не схлопываются через `html`), поля вложенных блоков внутри ячейки и `inline-block` (`taffy` теряет их в режиме только-измерения, поэтому ячейка и атомарный строчный раскладываются целиком), правило квирков (строка только из картинок без «стойки»), ширина колонок по `width` ячеек и проценты, высота ячейки как минимум; кроме того, `<wbr>`, потерянные скобки в сериализации значений (`calc((a - b) / 2)`), размещение элементов сетки (`grid-area` и др.; `rustdoc_all` 2.5% → 99.9%), закрытый `<details>`, кернинг при метриках профиля, контейнер `fixed`/`absolute` размером с вьюпорт.
- **Собственное дерево `taffy`** (`layout/full/tree.rs`): алгоритмы `taffy` на наших узлах. Даёт `calc()` в длинах (высокоуровневый `TaffyTree` его не резолвит), узлы с собственным алгоритмом и хранение фрагментов.
- **Сетка:** `grid-template-columns/rows` (длины, `%`, `fr`, `auto`, `min/max-content`, `minmax()`, `fit-content()`, `repeat()`, `auto-fill/auto-fit`).
- **Строчный контекст** (`layout/full/ifc.rs`, `build.rs`, `font.rs`): блочный контейнер со строчным содержимым получает анонимные блоки; текст шейпится один раз на текстовый узел; жадный перенос по UAX#14; схлопывание пробелов для `normal`/`nowrap`/`pre`/`pre-wrap`/`pre-line`; строчные боксы с отступами/рамками через перенос; атомарные (`inline-block`, `inline-flex`, `inline-table`, `img` и т. п.) с shrink-to-fit и базовой линией по последней строке; `<br>`; `text-align`; `line-height`; вертикальные метрики по правилам Blink (округлённые ascent/descent, полу-лидинг с округлением вниз); жирный и курсив меряются настоящими лицами, а не таблицей метрик профиля (она описывает обычное начертание).
- **Таблицы** (`layout/full/table.rs`): автоматическая раскладка CSS 2.1 §17.5.2 в упрощении — ширины колонок по min/max-content ячеек (избыток `colspan` делится пропорционально), `border-collapse: collapse` (рамки схлопываются, ячейке достаются половины) и `separate` с `border-spacing`, `colspan`/`rowspan`, `th` (жирный по центру), `vertical-align: top|middle|bottom` у ячеек, порядок `thead`/`tbody`/`tfoot`.
- **float/clear:** стили передаются `taffy` (`float_layout`).
- **Процентные вертикальные `padding`/`margin`:** `taffy` считает их от высоты родителя (CSS — от ширины); `Full` делает второй проход, подставляя длины от ширины блока-контейнера, только когда такие значения есть.
- **Запросы:** `getBoundingClientRect` для строчного элемента и текстового узла — объединение фрагментов; `getClientRects` — как в Blink: по прямоугольнику на строку у элемента с отступами/рамками, по прямоугольнику на текстовый фрагмент у элемента без них.
- **Отрисовка в `Full`:** готовые строки рисуются там, где их положила раскладка (`PaintBox::text_baseline`), фоны и рамки строчных элементов — по фрагментам. На example.com текст центрируется и переносится как в Chrome.

Не сделано из этапа 3:
- **`vertical-align` у строчных** — сделан (`baseline`, `sub`, `super`, `middle`, `text-top`, `text-bottom`, `top`, `bottom`, длины и проценты; считается построчно в `place()`). `order` сортирует элементы flex/grid (в `taffy` его нет). `list-style`/`list-style-type` разобраны; пустой `li` с маркером высотой в строку. Не сделан сам `::marker` (ширина и рисование).
- **Единицы Blink** (`LayoutUnit`): отступы, поля, размеры и смещения в `Full` округляются вниз до 1/64 px, высота строки — до ближайшей 1/64, ширины рамок — вниз до целых физических пикселей (`1.7px` при DPR 2 даёт `1.5px`), `line-height` в `em`/`%` вычисляется в длину до наследования. Без этого разница плавающих сумм давала дрейф в пиксель на 4000px страницы: gnu.org 67% → 99.8%. Осталось: Википедия (тексты на письменностях вне вшитых шрифтов), ширины глифов вне вшитых шрифтов (`ⓘ`, эмодзи) в `rustdoc`.
- **Раскладка в физических пикселях.** Blink при масштабе устройства 2 считает страницу как при зуме 2: всё в физических пикселях, наружу отдаёт делённым на 2. `Full` делает так же, параметризуя округления через `dpr` (`Metrics::of(font, os, dpr)`, `quantize`, `line_height_px`, `snap_borders`): ascent/descent/line gap — до целого физического пикселя (строка Arial 16px — 18.5 CSS px), полу-лидинг — вниз до физического пикселя, длины — вниз до 1/64 физического, `line-height` — до ближайшей 1/64 физического. Вертикальные метрики профиля (`text/metrics_table.rs`): для 14 семейств — доли em (ascent/descent/line gap, округляются до физических пикселей; подобраны по снятым с Chrome значениям, совпадают на 1675–1681 из 1681 размеров), для `Times`/`Helvetica`/`Courier` — таблица `vmetrics_macos.bin` (метрики шрифта идут из таблиц внутри него и не следуют доле размера): физические размеры 4–144px с шагом 1/12. Высота `x` (`vertical-align: middle`, `ex`) — доля em по семейству, у `system-ui` — таблица по CSS-размеру (оптические размеры: `fmetrics_system_ui.bin`, снята при 2x). Размеры полей ввода: ширина `input` — `ceil(size·A + M − A)` в физических пикселях, где `A` — средняя ширина символа (доля em семейства, округляется вверх, если дробная часть ≥ ½), `M` — ширина самого широкого, `textarea` — `ceil(cols·A + 16·dpr)`; у `Helvetica`/`Times`/`Monaco`/`Courier`/`Lucida Grande` `A` — ширина `0`; поля `system-ui` — таблица. Шрифт полей ввода по умолчанию в Chrome-эталоне — `Arial` (в `ua_full.css`). Проверено: размеры 2x в CSS-пикселях совпадают с размерами вдвое больше при масштабе 1 для всех 17 семейств (кроме `system-ui`, у которого оптический размер зависит от CSS-размера). Результат (против эталонов с настоящим 2x): Rust Book (было 43.5% против эмуляции) 99.1%, lobste.rs (было 41%) 97.0%, text.npr.org 100%; остальные страницы не потеряли.
- **Четыре новые страницы** (`real/web_lobsters`, `web_rustbook`, `web_httpbin`, `web_npr`): lobste.rs **97.0%**, учебник Rust (глава 4.1) **99.1%**, httpbin (формы) **76.1%**, text.npr.org **100%**. Остальные: rustdoc 99.7–100%, gnu.org 100%, HN 98.6%, `example.com` 100%, Python docs 98.6%, Википедия 15.5% (шрифты хоста для письменностей вне вшитых). Что нашли: `fieldset`/`legend` (легенда поверх рамки, float + clear), базовая линия `checkbox`/`radio` (по нижнему краю рамки) и `textarea` (нет базовой линии), одно-двоеточечные `:before`/`:after`, логические `border-block`/`-inline`, смещения `position: sticky` (при прокрутке 0), строка из одних схлопываемых пробелов не занимает места (кроме `pre`).
- Не сделано по новым страницам: `justify-self` у блочных боксов (центрирование `fit-content`, `lobste.rs` «upvoter»), размеры `input[type=time|date|…|file]` (зависят от локали), ширины глифов `system-ui` на нескольких размерах (оптические размеры SF меняют advance), пустой `<span>` в потоке (прямоугольник на позиции в потоке), кернинг пробела через границу элемента (`3. ` перед ссылкой в `h1` у Python docs).
- **`<details>`**: содержимое — блок-контекст форматирования (поля внутри элемента), закрытое раскладывается (у него есть прямоугольники, как в Chrome) в боксе нулевой высоты и не рисуется (`Node::paint_hidden`). `rustdoc` против Chrome: 99.5–100% по всем шести страницам (оставшееся — ширины глифов вне вшитых шрифтов).
- **`transform`** (2D: `translate*`, `scale*`, `rotate`, `skew*`, `matrix`; поворот вокруг центра бокса) применяется к прямоугольникам, которые отдают `getBoundingClientRect`/`getClientRects`, включая потомков; рисование и `transform-origin` — нет. `position: sticky` стоит на статической позиции (у верха страницы смещение не действует; элемент выше своего `top` Chrome сдвинул бы). Шорткат `grid-template` разобран (строки / колонки, области строками). Переносы между ASCII-символами — по таблице, снятой с Chrome (`text/breaks.rs`: ICU закрывает `++`, `!a`, `/a` и открывает `-(`, `"(`, которые UAX#14 закрывает/открывает иначе).
- **Обтекание float-ов текстом** — сделано: строки IFC берут место из контекста блока (`BlockContext::find_content_slot`), строка, в которую не влезает слово, уходит под float-ы; узлы IFC теперь `Display::Block` (иначе `taffy` считал их боксом, избегающим float-ов целиком). Строка проверяется по `y` её верха, не по всей высоте.
- **`clear` у float разной высоты** (2 промаха в корпусе): ошибка на единицу в `taffy 0.12.2` (`cleared_threshold` берёт предпоследний сегмент, когда очищаемый float выше соседнего). Содержимое строк float не обтекает: текст рядом с float перекрывает его.
- **Псевдоэлементы `::before`/`::after`** — сделаны (`Stylist` хранит их правила только в `Full`, `StyleTree` стилизует их под id за концом документа, билдер ставит бокс первым/последним ребёнком; строки с экранированием, `attr()`, кавычки, `url(data:…)` с размером из SVG/PNG/GIF). Счётчики (`counter-reset`/`-increment`/`-set`, `counter()`, `counters()`, стили decimal, alpha, roman, leading-zero) сделаны по порядку обхода дерева. Не сделано: `url()` не с `data:` (размер неизвестен), `::marker`, `::first-line`/`::first-letter`, `quotes` и вложенность кавычек.
- **Статическая позиция** — сделана: перенесённый блок с `auto` в смещениях берёт позицию пустого маркера, оставленного в потоке родителя (во flex/grid маркер сам вне потока — позицию выбирает `taffy`). Не сделана для таблиц; для строчного блока `y` — верх строки, `x` — курсор строки.
- Контролы форм — сделаны размеры текстовых полей, `textarea`, кнопок, `select` (по формулам Blink, сверенным с Chrome для Arial; ширина символа — полкегля, у моноширинных 0.6, шрифт контролов по умолчанию — `system-ui` → без SF), `checkbox`/`radio`, базовые линии, центрирование содержимого кнопки по вертикали. Не сделано: `range`, `color`, `file`, `date`, список `select multiple`/`size>1`, подписи кнопок не на английском, виды контролов при `appearance`.
- Таблицы: `caption`, `col`/`colgroup`, `table-layout: fixed`, выравнивание ячеек по `baseline`, распределение заданной высоты таблицы по строкам.
- `text-align: justify`, bidi (арабский рисуется в своём порядке, смешанные строки — нет), `display: contents`, float-ы внутри строчных выносятся перед строками, где встретились (в Chrome — на текущую строку), `position: sticky`, scroll-контейнеры, собственные размеры `img`/контролов форм, маркеры списков.
- **Инкрементальная раскладка**: как договорено (Q6), дерево пересобирается по `dirty_epoch`. Стоимость (release, страница из 3000 абзацев с вложенными `span` и таблицы 300×6, около 9 тыс. текстовых фрагментов): первая раскладка `Full` 357 мс против 161 мс у `Legacy`, после мутации DOM 366 мс против 179 мс. Почти всё — построение (шейпинг текста и разбор шрифтов; сама раскладка 5 мс), поэтому инкрементальность нужна прежде всего построению. Разобранные лица кешируются на поток (`text::shaper::face`), шрифты и метрики — на построитель; дальше — кеш шейпинга по тексту и шрифту.
- **Перед тем как сделать `Full` режимом по умолчанию в headless:** расширить корпус реальными страницами (локально, вне git), прогнать `BENCHMARK.md` (routed 118/126) и стелс-бенчи на нужной сети (за владельцем), измерить стоимость `Full` на больших страницах.

**Что M1 показал про раскладку** (это вход для этапов 1–3):
1. `body` с любым строчным ребёнком (текст, `input`, `button`) целиком превращается во flex-строку (`engine.rs:566`) — заголовок, карточка и ряд блоков выстраиваются в одну линию. Это самый заметный дефект и главный аргумент за настоящий IFC.
2. `background:` (шорткат) и цвета рамок не разбираются вовсе — рамки рисуются цветом текста.
3. `<input value>` не показывает значение, `<button>` не центрирует подпись: у контролов нет собственных размеров и внутренностей.
4. Заголовки, отступы и размеры шрифта UA не применяются (нет UA-таблицы), поэтому `<h1>` выглядит как абзац.
5. Реальные страницы (release, профиль `chrome_148_macos` на Windows-хосте):
   - Hacker News узнаваем, но таблицы не раскладываются (нет табличного алгоритма): строки ленты расползаются по горизонтали, «очки/автор/время» уезжают в следующую строку. Аргумент за таблицы в этапе 3.
   - example.com: слова слипаются, а буквы разъезжаются (`Thi sdomai ni sf or...`), для CJK/тайского/арабского рисуются «тофу»-квадраты. Наблюдение, причина не изучена: похоже, для семейств macOS-профиля на Windows-хосте нет реальных шрифтов, и берутся приблизительные метрики/подстановка. Это ровно тот вопрос «откуда брать шрифты профиля», который в плане вынесен в этап 2 и требует решения до его начала.
   - **Проверено на macOS (2026-09-30, `examples/screenshot`, release):** воспроизводится, значит не зависит от ОС хоста, и это два разных дефекта.
   - *«Тофу» для CJK/арабского/тайского/эмодзи — покрытие шрифтов.* Шрифты вшиты в крейт (`canvas/fonts`: Liberation Sans/Serif/Mono, DejaVu Sans, Noto Sans), системные не подгружаются (`fontdb` без `default-features`), глифов этих письменностей в них нет. Латиница и кириллица на локальной странице рисуются правильно.
   - *Слипшиеся слова и разъехавшиеся буквы — не шрифты, а раскладка.* `/s.js` на example.com оборачивает каждую букву в `<span>` (`replace(/./gu,"<span>$&</span>")`). Без строчного контекста (L1) каждый span становится flex-элементом шириной 0.6em на символ (T1), а span из одного пробела схлопывается (T5). Тот же текст без скрипта, с тем же CSS и теми же шрифтами, рисуется правильно (перенос строк, семейства `system-ui`/`sans-serif`, шорткат `font` проверены отдельно). Исправляется этапом 3 (IFC) и этапом 2 (измерение текста), а не подбором шрифтов.
   - *Ещё дефект:* `text-align: center` не применяется (у example.com `text-align:center` на `body`, текст нарисован по левому краю) — тоже этап 3 (IFC).
6. Навигация по сети в debug-сборке не работает (переполнение стека в существующем `getting_started` — проблема не M1); проверять сеть нужно в `--release`.

## 0. Цель и границы

**Цель.** Одна кодовая база движка и две сборки:

| Сборка | Команда | Что внутри |
|---|---|---|
| Headless (как сейчас) | `cargo build -p browser_oxide` | движок без отрисовки и без оконных зависимостей |
| Headless + скриншоты | `cargo build -p browser_oxide --features paint` | + display list и растеризация в Skia, `Page::screenshot()` |
| С интерфейсом | `cargo build -p browser_oxide_shell` | окно, вкладки, адресная строка, devtools; движок с `paint` |

**Жёсткие инварианты.**

1. Headless-сборка не тянет оконных зависимостей (winit, egui, wgpu, softbuffer). Проверяется в CI через `cargo tree`.
2. Отпечаток headless-сборки не меняется из-за самого факта существования GUI: весь код отрисовки и окна — за фичей `paint` / в отдельном крейте.
3. Исключение из п. 2 осознанное: этапы 1–3 (стили, текст, раскладка) исправляют геометрию и в headless. Это меняет `getBoundingClientRect`/`offsetWidth` — поэтому каждый такой этап проходит сравнение с Chrome и прогон `BENCHMARK.md` (routed 118/126 не должен падать), а новая раскладка вводится за рантайм-переключателем до подтверждения.
4. Политика линтов (`-D warnings`, allow только с `reason`), лицензии (MIT/Apache, проверка `deny.toml`), тесты в один поток — без изменений.

**Вне рамок первой версии:** воспроизведение видео/аудио, GPU-композитинг со слоями, writing modes, печать, расширения, синхронизация профилей.

| E5 | Генератор поведения (`humanize.js`, `stealth/behavior.rs`) рассчитан на синтетику | `input_ext.rs` | В GUI будет накладываться на реальный ввод |
| E6 | `host::EngineHandle` умеет только `navigate`/`evaluate`/`query_text` | `host/mod.rs:73` | Для окна нужен двусторонний канал команд и событий |
| E7 | Фреймы: same-origin — реалмы в том же изоляте, cross-origin — отдельные изоляты `ChildIframe` со своими DOM и раскладкой; ограничение V8 на порядок уничтожения изолятов | `frames.rs`, `iframe.rs:20` | Композитинг фреймов и маршрутизация ввода в дочерние изоляты — отдельная работа |

### 1.5 Что уже готово и переиспользуется

- Skia (`skia-safe`) — растеризатор уже в зависимостях, canvas рисует через него.
- Шейпинг `rustybuzz`, растеризация глифов `swash`, `fontdb`, таблица метрик — в `canvas/text/`.
- Декодирование PNG/JPEG (`image`), готовые RGBA-буферы изображений.
- taffy (block/flex/grid), парсеры CSS/селекторов/значений, модули `cascade`/`layers`/`media`.
- Доверенные события (`markTrusted`, `isTrusted` через WeakSet) — `event_bootstrap.js`.
- `sync_frame_geometry`, `drive_children` для фреймов; devview с панелями DOM/сети/консоли и сравнением свойств engine-vs-Chrome (`INSPECT_PROPS`).
- `LayoutEngine::dirty_epoch`, `set_viewport`, `Viewport::with_dpr`.

## 2. Целевая архитектура

```
crates/browser_oxide/src/
  style/        НОВЫЙ  единый движок стилей: каскад → ComputedStyle-дерево с наследованием,
                       инвалидация; им пользуются и раскладка, и getComputedStyle
  text/         НОВЫЙ  вынесено из canvas/text: шрифты, фолбэк, шейпинг, UAX#14, bidi
  layout/       ПЕРЕРАБОТКА  дерево боксов → taffy (block/flex/grid) + свой IFC, таблицы, floats
                       → дерево фрагментов; прокрутка; хит-тест
  paint/        НОВЫЙ, feature "paint"  display list + растеризация Skia, скриншоты
  render/       НОВЫЙ  тактирование кадров и шаги "update the rendering"
  input/        НОВЫЙ  нативный конвейер ввода: хит-тест → доверенные события → действия
                       по умолчанию, фокус, редактирование
  host/         РАСШИРЕНИЕ  канал команд/событий для интерактивного режима

crates/browser_oxide_shell/   НОВЫЙ, publish = false
  eframe (egui + winit + wgpu) — хром браузера; контент — текстура из растра движка
```

Поток данных за кадр:

```
DOM-мутации / ввод ─► style (инкрементально) ─► box tree ─► layout ─► fragment tree
                                                                         │
                         хит-тест, geometry API, observers ◄─────────────┤
                                                                         ▼
                                                     display list ─► Skia raster ─► PNG | окно
```

**Почему отдельный крейт, а не фича `gui` в движке.** Оконный стек тяжёлый и платформенный. В отдельном крейте его зависимости физически не попадают в дерево `browser_oxide`, опубликованный крейт не меняется, а CI может собирать shell отдельной задачей. В `Cargo.toml` воркспейса shell добавляется в `members`, но не в `default-members`, чтобы `cargo build` по умолчанию собирал только headless.

**Почему `paint` — фича движка, а не часть shell.** Скриншоты нужны headless-пользователям (MCP, Python, CDP `Page.captureScreenshot`), а растеризатор должен работать на том же потоке, что и `Page` (`!Send`).

## 3. Этапы

Оценки — человеко-недели для одного разработчика, знакомого с кодовой базой. Этапы 1–3 последовательны по смыслу, 4 можно начать раньше на старой раскладке (см. веху M1).

### Этап 0. Каркас и разделение сборок — 1–2 нед.

Задачи:
1. Дождаться, пока текущая незакоммиченная работа по фреймам/реалмам (`frames.rs`, `realms.rs`, `privileged.rs`) будет смержена: она затрагивает `page.rs` и `iframe.rs`, которые трогают этапы 5–6.
2. Создать `crates/browser_oxide_shell` (`publish = false`, `[lints] workspace = true`). Добавить `default-members = ["crates/browser_oxide", "crates/browser_oxide_mcp"]`.
3. Фича `paint` в `browser_oxide` (пока пустой модуль `paint`).
4. Расширить `host`: `EngineHandle::spawn_interactive()` с каналами
   - команды: `Navigate`, `Back`, `Forward`, `Reload`, `Stop`, `Resize{w,h,dpr}`, `Input(InputEvent)`, `Evaluate`, `Shutdown`;
   - события: `FrameReady{pixels|display_list, damage}`, `UrlChanged`, `TitleChanged`, `LoadState`, `CursorChanged`, `Console`, `Dialog`, `NewWindowRequested`.
5. CI: задача сборки shell (Windows/Linux/macOS) + clippy; проверка `cargo tree -p browser_oxide -e normal` на отсутствие `winit|egui|wgpu|softbuffer`; новые лицензии в `deny.toml`.
6. Shell: окно с адресной строкой, навигация, в области контента — текст страницы (`PageSnapshot.text`).

Критерии готовности: три команды сборки из п. 0 работают; headless-дерево зависимостей не изменилось.

### Этап 1. Единый движок стилей — 4–6 нед. (затрагивает headless)

Задачи:
1. Модуль `style`: проход по DOM сверху вниз, для каждого элемента — каскад с учётом origin (UA → user → author), `!important`, `@layer` (через готовые `css_cascade::cascade_sort`/`LayerOrder`), `@media` (готовый `evaluate_media_query`), `@supports`. Результат — `ComputedStyle` с родителем (наследование, `inherit`/`unset`/`revert`, `currentColor`, `em`/`rem`/`%`/`vw`/`ch` от реального `font-size`).
2. `StyleRule.declarations` → упорядоченный `Vec` (сохраняет порядок внутри правила), разбор деклараций — один раз при загрузке листа, а не на каждый матч (сейчас `match_rules` сериализует и заново парсит каждое правило на каждый элемент).
3. UA-стили — настоящий CSS-лист (собственная реализация по разделу Rendering спецификации HTML), вместо `ua_declarations` и `HIDDEN`. Презентационные атрибуты — через тот же каскад.
4. Ускорение: хеширование правил по самому правому id/class/tag, bloom-фильтр предков, кеш стилей для одинаковых соседей.
5. Инвалидация: мутации DOM (атрибуты, классы, вставка/удаление, смена состояния) помечают узлы; пересчитывается только затронутое. `dirty_epoch` сохраняет семантику.
6. Псевдоэлементы `::before`/`::after` (`content`: строки, `attr()`, счётчики — базово), `::marker`, `::placeholder`, `::selection`.
7. Состояния элементов (`hover`, `active`, `focus`, `focus-visible`, `focus-within`, `checked`, `disabled`, `placeholder-shown`) — поля в `ElementData`, их выставляет ввод (этап 6).
8. Расширить `PropertyId` до набора, нужного для отрисовки (см. S6), с корректными начальными значениями и флагами наследования.
9. `getComputedStyle` читает из того же `ComputedStyle` (удалить отдельный путь в `dom_ext.rs`). Сериализация значений — как в Chrome (существующие тесты паритета остаются зелёными).

Критерии: тесты наследования/каскада; `getComputedStyle` и раскладка согласованы; `benches/page_throughput` не хуже текущего более чем на 10%; `BENCHMARK.md` не падает.

### Этап 2. Текст и шрифты — 3–5 нед. (затрагивает headless)

Задачи:
1. Вынести `canvas/text/*` в общий модуль `text`; canvas переходит на него без изменения вывода (тест `png_byte_parity` и прочие тесты canvas — зелёные).
2. Подбор шрифта по CSS Fonts: список семейств, generic-семейства, weight/style/stretch, пофонтовый фолбэк для отсутствующих глифов (CJK, эмодзи).
3. **Набор шрифтов берётся из стелс-профиля, а не из системы хоста.** Font fingerprinting через ширину `<span>` в разных `font-family` — классическая проверка; macOS-профиль на Windows-хосте не должен измерять текст шрифтами Windows. Для отрисовки нужны либо поставляемые метрически совместимые шрифты (с подходящей лицензией — OFL/Apache), либо системные с подменой метрик по `metrics_table`. Решение фиксируется до начала этапа.
4. Разрывы строк UAX#14 (`unicode-linebreak`), графемы (`unicode-segmentation`), bidi (`unicode-bidi`) — все MIT/Apache.
5. `@font-face`: загрузка через `net`, декодирование WOFF/WOFF2 (brotli уже есть; декодер WOFF2 — проверить лицензию или написать свой), `document.fonts`/`FontFace` с реальными состояниями загрузки, `font-display`.
6. API измерения для раскладки: шейпинг прогона со стилем → глифы, advances, ascent/descent, возможности переноса.

Критерии: ширины текста для эталонных строк совпадают с Chrome того же профиля в пределах 1px; тесты шрифтового фингерпринта (сравнение с эталонными снимками Chrome) не хуже текущих.

### Этап 3. Раскладка: IFC, дерево боксов и фрагментов — 6–9 нед. (самый рискованный, затрагивает headless)

Задачи:
1. **Дерево боксов** отдельно от DOM: анонимные блочные/строчные боксы (block-in-inline), `display: contents`, псевдоэлементы, маркеры списков, `display: none`.
2. **Переход с `TaffyTree` на собственное дерево**, реализующее трейты taffy (`LayoutPartialTree` и др.). taffy остаётся для block/flex/grid, а свои режимы (IFC, таблицы) подключаются как отдельные алгоритмы; кеш taffy по узлам даёт инкрементальную раскладку (решает L2).
3. **IFC**: строчные боксы, строчные элементы с padding/border/margin через перенос, атомарные inline (`inline-block`, `img`, `inline-flex`), `vertical-align`, `line-height`, `text-align`, `text-indent`, все режимы `white-space`, `word-break`/`overflow-wrap`, `text-overflow: ellipsis`. Удалить хак `flex-row-wrap` (`engine.rs:566`).
4. **Дерево фрагментов** — выход раскладки: у бокса может быть несколько фрагментов. На нём строятся `getBoundingClientRect`, `getClientRects`, `Range.getBoundingClientRect`, `offset*`, `client*`, `scroll*`, `elementFromPoint`/`elementsFromPoint`.
5. Позиционирование: containing block по спецификации (padding box позиционированного предка), `fixed` относительно вьюпорта с учётом прокрутки, `sticky`, `z-index` (для отрисовки — этап 4).
6. Floats и `clear` (проверить поддержку в версии taffy; иначе своя реализация внутри BFC), таблицы (свой алгоритм; как временная мера — сопоставление с grid).
7. **Прокрутка**: scroll-контейнеры для `overflow: auto|scroll|hidden`, scrollable overflow area, `scrollTop/Left`, `scrollTo`/`scrollBy`/`scrollIntoView`, событие `scroll`. `window.scrollX/Y` — из состояния раскладки через op вместо JS-переменной (`window_bootstrap.js:1704`). Смещения прокрутки и `transform` учитываются в геометрии (решает L7).
8. Заменяемые элементы: внутренние размеры `img` из декодированного изображения (связать `fetch_ext` с раскладкой), `object-fit`/`object-position`, `canvas`/`video`/`iframe` 300×150, внутренние размеры контролов форм как в Chrome.
9. SVG: собственный размер и viewBox; внутренняя геометрия — для `getBBox` и отрисовки (этап 4).
10. IntersectionObserver и ResizeObserver на реальной геометрии.
11. **Переключатель раскладки** `LayoutMode::{Legacy, Full}` в опциях страницы: на время перехода headless можно откатить на старую приближённую раскладку.

Критерии: корпус эталонных страниц (сохранённых локально, без сети) с прямоугольниками из Chrome — автоматический тест, процент совпадений в пределах допуска растёт и фиксируется в CI; переход `Full` по умолчанию — только если стелс-бенчмарк не хуже.

### Этап 4. Отрисовка (`feature = "paint"`) — 5–7 нед.

Задачи:
1. **Display list**: прямоугольник, граница (стили сторон, цвета, радиусы), прогон текста (глифы + шрифт + цвет + декорации), изображение, градиент, тень, clip push/pop (прямоугольник, скруглённый), opacity-группа, transform push/pop, ссылка на surface canvas, ссылка на подфрейм, скроллбар.
2. Построение из дерева фрагментов в порядке CSS 2.1 Appendix E со stacking contexts (z-index, opacity < 1, transform, filter, `position: fixed/sticky`, `isolation`).
3. Фоны (цвет, `url()`, linear/radial/conic-градиенты, size/position/repeat/clip/origin, несколько слоёв), границы всех стилей, `border-radius`, `outline`, `box-shadow`, `text-decoration`, `text-shadow`, `opacity`, `visibility`, клиппинг `overflow`, 2D-трансформы.
4. Растеризатор: Skia raster surface на CPU, детерминированный (для скриншотов и тестов). GPU-бэкенд — этап 8.
5. Кеш изображений (декодированный RGBA по URL + размеры), позже анимированные GIF/WebP.
6. `<canvas>`: прямая ссылка на существующую Skia-поверхность `Canvas2D` без копирования; WebGL — через фичу `webgl-render`.
7. SVG: рендер inline-SVG и `<img src=*.svg>`. Кандидат — `resvg`/`usvg`, если лицензия проходит `deny.toml`; иначе свой рендер подмножества на Skia.
8. Нативный вид контролов форм в стиле Chrome: checkbox, radio, text/password/search, button, select, range, progress, textarea, placeholder.
9. API: `Page::screenshot(ScreenshotOptions { full_page, clip, format, scale })`; CDP `Page.captureScreenshot`; инструмент `screenshot` в MCP; метод в Python-биндинге.
10. Инвариант: отрисовка страницы не влияет на отпечатанные поверхности — вывод `canvas.toDataURL`/WebGL остаётся прежним.

Критерии: golden-image тесты (подмножество reftest-ов WPT для фонов/границ/текста, свои эталоны) со сравнением с допуском; скриншот 1920×1080 страницы средней сложности — < 50 мс на CPU (release).

### Этап 5. Цикл рендеринга — 2–3 нед.

Задачи:
1. Модуль `render`: шаги «update the rendering» из HTML — события resize/scroll → rAF-колбэки → стиль → раскладка → ResizeObserver → IntersectionObserver → paint → кадр.
2. Часы кадров: в headless — виртуальные, с текущей каденцией и джиттером (поведение rAF для детекторов не меняется); в headed — vsync из winit.
3. rAF переходит с `setTimeout` на часы кадров (`timer_bootstrap.js:232`).
4. Интерактивный режим цикла событий `Page::run_interactive(commands)`: не завершается по простою, совмещает кадры, `drive_children` для фреймов, сеть, таймеры.
5. Коалесцирование `pointermove`/`mousemove` до одного на кадр, `getCoalescedEvents()`/`getPredictedEvents()` — как в Chrome.
6. CSS transitions и `@keyframes`-анимации для `opacity`/`transform`/цветов/размеров; Web Animations — базово.
7. Damage tracking: перерисовка только изменённых областей.

Критерии: стабильные 60 fps на статической странице при прокрутке; тесты каденции rAF и стелс-тесты в headless не меняются.

### Этап 6. Ввод и взаимодействие — 4–6 нед.

Задачи:
1. Модуль `input`: `InputEvent` (мышь: move/down/up/wheel; клавиатура: down/up с `code`/`key`/`text`; IME: preedit/commit; тач) → хит-тест по фрагментам (`pointer-events`, `visibility`, клиппинг, фреймы с пересчётом координат и маршрутизацией в дочерние изоляты) → доверенные события через привилегированный op, а не через `evaluate` строки.
2. Последовательности по UI Events: pointerover/enter/move/down/up, mouse*, click/dblclick/auxclick/contextmenu, focus/blur/focusin/focusout, wheel → прокрутка (плавная).
3. CDP `Input.dispatchMouseEvent`/`dispatchKeyEvent` в `protocol/session.rs` переводятся на тот же конвейер (тесты `cdp_input_fidelity`, `default_click_actions` остаются зелёными).
4. Фокус: tab-порядок, `tabindex`, `:focus-visible`, `document.activeElement`.
5. Редактирование: каретка и выделение, привязанные к позициям в раскладке (`Selection`/`Range`, `caretPositionFromPoint`), правка `input`/`textarea` с `beforeinput`/`input`/`composition*`, IME, буфер обмена (`arboard` в shell), базовый `contenteditable`, выделение текста мышью.
6. Действия по умолчанию: переход по ссылке (`target=_blank` → новая вкладка), отправка форм, активация `label`, checkbox/radio, выпадающий список `select` (свой попап), `cursor` → курсор ОС.
7. **Источник ввода**: `InputSource::{Real, Synthetic}`. При реальном вводе генератор `humanize.js`/`behavior.rs` не вмешивается; синтетика остаётся для API автоматизации. `event.timeStamp` — из времени события ОС.

Критерии: ручной сценарий «вход на сайт с формой логина, поиск, прокрутка ленты» проходит в shell; тесты ввода headless не регрессируют.

### Этап 7. Оболочка браузера — 3–5 нед.

Задачи:
1. `eframe` (egui + winit + wgpu): хром браузера нарисован egui, контент — текстура из растра движка, обновляется по `FrameReady` с damage-областями.
2. **Вкладка = отдельный поток движка** со своим `EngineHandle`: `Page` и изоляты V8 привязаны к потоку, а порядок уничтожения изолятов на одном потоке — известная ловушка (см. «кладбище изолятов» в `iframe.rs`).
3. Адресная строка (URL/поиск), назад/вперёд/обновить/стоп (история сессии — проверить и довести в `nav_ext`), индикатор загрузки, заголовок и favicon, поиск по странице, масштаб.
4. Диалоги `alert`/`confirm`/`prompt`/`beforeunload`, выбор файла для `<input type=file>`, контекстное меню, загрузки (базово).
5. Выбор стелс-профиля на вкладку; каталог профиля для cookies/storage.
6. Панель devtools, переносящая функции devview: дерево DOM, консоль, сеть (`net::netlog`), сравнение engine-vs-Chrome, поверхности canvas, трассировка.
7. Доступность: `accesskit` (MIT/Apache) для хрома, позже — дерево доступности страницы.

Критерии: в shell можно открыть несколько вкладок, ходить по истории, пользоваться devtools; закрытие вкладки не роняет процесс.

### Этап 8. Полнота и производительность — постоянно

- 3D-трансформы, `filter`, `backdrop-filter`, `clip-path`, `mask`, multi-column, writing modes, `position: sticky` в сложных случаях.
- GPU-растеризация Skia (GL/D3D/Metal/Vulkan) в shell, тайлинг, слои, композиторная прокрутка без перерисовки, растеризация в отдельном потоке.
- `<video>`/`<audio>` — как минимум постер и контролы; воспроизведение — отдельное решение (лицензии кодеков).
- Профилирование памяти: бюджеты на display list и кеши.

## 4. Стелс: что учесть в headed-режиме

1. **Размеры окна и экрана.** `screen.*`, `outerWidth/Height`, `innerWidth/Height`, `devicePixelRatio` обязаны согласовываться между собой и с профилем. По умолчанию — окно контента фиксируется на `inner`-размере профиля (при необходимости с масштабированием растра под физический DPR монитора); опционально — «живой» профиль, выведенный из реального монитора.
2. **Масштаб страницы** меняет `devicePixelRatio` и медиазапросы — как в Chrome, но с согласованием с профилем.
3. **Шрифты** — из профиля, не с хоста (см. этап 2).
4. **WebGL/GPU**: отрисовка окна через wgpu хоста не должна протекать в `WEBGL_debug_renderer_info` — WebGL-идентичность остаётся профильной.
5. **Реальный ввод**: коалесцирование событий по кадрам, реалистичные `timeStamp`, отключение синтетического генератора поведения (этапы 5–6).
6. **Headless не меняется от GUI**: CI-задача прогоняет стелс-тесты для сборок с `paint` и без; расхождения — ошибка.

## 5. Тестирование

- **Корпус раскладки vs Chrome.** Превратить сравнение `INSPECT_PROPS` из devview в автоматический тест: набор сохранённых страниц + эталонные прямоугольники и computed styles из Chrome (снимаются офлайн, в CI сети нет). Метрика — доля узлов в пределах допуска; не должна падать.
- **Golden images** для отрисовки с допуском по пикселям; эталоны — из Chrome того же профиля и из собственных утверждённых снимков.
- **Подмножество WPT** (reftests CSS 2.1, css-text, css-backgrounds, css-flexbox) — прогон по желанию, отдельный отчёт.
- **Производительность**: `benches/page_throughput` + новые бенчи стиля, раскладки, отрисовки, задержки кадра.
- **Стелс-регрессии**: существующие тесты + `BENCHMARK.md` после этапов 1, 2, 3.
- Все тесты — `--test-threads=1`, сетевые — `#[ignore]`.

## 8. Риски

| Риск | Вероятность | Митигирование |
|---|---|---|
| IFC и дерево фрагментов сложнее оценки | высокая | Сначала только LTR без floats, bidi и floats — вторым проходом; переключатель `LayoutMode` |
| Исправленная геометрия ухудшает стелс-результаты | средняя | Сравнение с Chrome до/после, `BENCHMARK.md` как гейт, откат на `Legacy` |
| Производительность полной пересборки стиля/раскладки на каждый кадр | высокая до этапа 3 | Инкрементальность в этапах 1 и 3; M1 допускает 5–10 fps |
| Ограничения taffy (floats, таблицы, IFC) | средняя | Собственное дерево через трейты taffy, свои алгоритмы для недостающих режимов |
| V8: изоляты и потоки при вкладках и фреймах | средняя | Поток на вкладку; существующее «кладбище изолятов» |
| Лицензии SVG/WOFF2/шрифтов | средняя | Проверка до начала этапа, запасной вариант — своя реализация |
| Параллельная незакоммиченная работа по фреймам | высокая сейчас | Этап 0 — после её слияния |
